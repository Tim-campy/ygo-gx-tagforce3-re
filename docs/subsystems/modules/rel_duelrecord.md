## Purpose and flow

Library module (id 0x14, `libduelrecord_rel`) showing the duel record: three tabs of statistics/achievements read from the save record table (`save_get_record_table`). Exports: `ui_duel_record_start(heap)` (+0x8), `ui_duel_record_update()` (+0xfc), `ui_duel_record_draw()` (+0x28c); callers rel_story, rel_title, rel_labo. Start uses the caller's heap or its own 0x200000-byte FPL.

States (word 0x9560): 0 loading `database/duelrecord.ehp` then building the lists, 1 fade-in, 2 browsing, 3 fade-out, 4 teardown (update returns 1).

Controls: cancel (`system_get_confirm_button(1)`) leaves; L/left and R/right/square cycle tabs; up/down scroll (wrap on a fresh press); on tab 2 the confirm button marks the entry under the cursor as selected (writes its id to record table +0x290) with a 16-frame flash.

## Key structures

Screen block 0x9560 (0x198 bytes): 0x9560 state; byte 0x9564 = current tab (low nibble) and tab count (high nibble, 3); byte 0x9565 completion percentage; 0x9566/0x9568 select flash flag/counter; 0x956a[3] scroll top; 0x9570[3] cursor; 0x9576 tab-2 scroll mode; 0x9578 visible count; 0x957a render top; 0x957c partial-line offset (in 0x18-pixel lines); 0x957e overflow lines; 0x9580 blink counter (0..0x50); 0x9582[3] entry counts; 0x9588[3] entry lists; 0x9594 save record table; 0x9598 heap; 0x959c/0x95a0 FPL; 0x95a8 layout set (0x150 bytes: archive +0, EHF members +0x124 + 4n).

Entry (16 bytes): u16 id +0, u16 ordinal +2, byte +4 (bits 0-1 new state, bit 2 has a value), u32 value +8, byte +0xc bits 0-5 line count (0x18 pixels per line, the view holds 9 lines), u16 +0xe tab-2 number.

Per-tab tables in `.data` (u16 per entry: bit 0 enabled, bits 1-15 dictionary word of the entry text): tab 0 at 0x9164 (0x31 entries), tab 1 at 0x91c8 (0x53), tab 2 at 0x9270 (0x68). Tab labels are dictionary words 0x11a + tab, the title 0x10f, the percentage label 0xd8.

Save record table as read here (offsets from `save_get_record_table()`): u32 values [0x31] at +0; tab-0 new flags u8 [0x31] at +0xc4 (cleared when shown); tab-1 states u8 [0x53] at +0xf8 (0 locked, 1 new, 2 seen); tab-2 states u8 [0x68] at +0x14c (0 not achieved, 1 new, 2 seen); tab-2 numbers u16 [0x68] at +0x1b8; selected tab-2 entry u16 at +0x290. Tab-1 entries 0-2 are computed: 0 = number of (character, variant) pairs with `save_test_character_flag_bit2` among the 0x8f characters that can duel, 1 = `save_get_duelist_level`, 2 = number of non-zero tab-2 states. Tab-0 value id 0x25 is shown as two 2-digit groups (value / 60, value % 60) and id 0x2b as three groups ((v / 6000) % 60, (v / 100) % 60, v % 100), i.e. durations; others as up to 9 digits, capped at 999999999.

Completion percentage = 100 x (achieved tab-2 entries + unlocked tab-1 entries) / (tab-2 entries + enabled tab-1 entries).

## Files and resources

- `database/duelrecord.ehp` under root 3 (USRDIR), one archive, loaded with `container_load_file` (name string at 0x93a4).
- Resource table 0x9380: 3 records of 12 bytes `{u16 id, cached member, member-name format}` (ids 0x1002 and 0x1003 GIM images, 0x1020 dictionary); the member name is formatted with the language letter from the 6-character string 0x93bc (the decompiler shows the first format pointer as `tab_gim`; exact strings to be read from `.data`).
- EHF layout names: a 6 x 0x40-byte table at 0x93c4 starting with `m_menu_bar01.ehf`; only index 4 is loaded (play range 0..0x1df) and drawn as the background.

## Shared code

`ui_duel_result_reset_sprite_state` and `ui_duel_result_draw_atlas_rect` are copies of rel_duel_mgr's result-screen helpers; the font wrappers are BOOT.BIN copies; the archive callback and resource search are rel_shop's.
